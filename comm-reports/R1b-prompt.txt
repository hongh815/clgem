## 분석 배경

사용자의 목표: clgem을 "비서(assistant)형 AI"가 아니라 **"상시 켜진 팀의 구성원(teammate)"** 으로 운용하는 것. 핵심 관심사: 작업내역·정보·취합 데이터를 한 곳에 누적하되, 토큰을 절약하면서도 지속 업무가 가능한 **단일 영속 데이터 저장소/장치**.

## 축① 단일 영속 데이터 저장소 (최우선)

### 현재 상태

- Comm.md가 "단일 공유 레저(single shared ledger)"로 정의됨 (SKILL.md:33).
- 섹션 구성: /goal, Status Summary, Agent Roster, Task Board, Worker Reports, Antigravity Review Log, Leader Decision Log, Open Items, Archive (Comm.template.md:1-66).
- 기록 원칙: append-only, never delete (SKILL.md:145-146).
- 파일이 커지면 Archive 섹션으로 이동만 허용 (SKILL.md:146).
- 장기 산출물은 `comm-reports/T<id>.md`에 별도 저장 후 링크 (SKILL.md:141).
- 토큰 절약은 **모델 선택 계층에만 적용** (agents.md:4-5, 20-34). Comm.md 자체의 토큰 관리 메커니즘 **언급 없음**.

### 팀원화 관점의 부족점

**P1. 토큰 비용 없는 선택적 로딩 메커니즘 없음**

Leader가 세션을 재개(Step 0, SKILL.md:40-41)할 때 Comm.md 전체를 읽어야 한다. append-only + Archive 정책은 파일의 물리적 삭제를 막지만, 어느 부분을 읽어야 하는지를 안내하는 인덱스나 계층 요약이 전혀 없다. 3개월·50태스크를 넘긴 장기 프로젝트에서는 Comm.md 단독으로 수만 토큰이 될 수 있다.

**P2. 롤업(roll-up) / 압축 규칙 없음**

Archive 이동만 허용되며 "어떤 조건에 Archive하는가", "Archive 전 요약을 생성하는가"에 대한 규칙이 없다 (SKILL.md:146 "if the file grows unwieldy"는 기준이 모호). 완료된 태스크의 전체 Worker Report와 Review Log가 모두 축적된다.

**P3. 구조화 색인·검색 없음**

Comm.md는 마크다운 플랫 파일이다. 태스크 ID·날짜·결정 키워드로 빠른 색인 조회, 특정 섹션만 선택적 로딩, 크로스-레퍼런스 추적이 불가능하다. 장기 운용 시 Leader가 과거 결정을 찾기 위해 파일 전체를 스캔해야 한다.

**P4. 세션 간 "재개 진입점" 정보가 Status Summary에 비공식으로만 존재**

`## Status Summary`는 "2-3 lines: where the project stands right now"로 정의되지만 (Comm.template.md:19-21), 재개 시 최소 필요 섹션 목록이나 "여기서부터 읽어라" 포인터가 없다. Leader가 재개할 때 전체를 읽을지 Status Summary만 읽을지 판단 기준이 없다.

**P5. comm-reports/T\<id\>.md 파일들의 인덱스 없음**

개별 태스크 보고서가 별도 파일로 분리되지만 Comm.md에서 링크만 걸 뿐, 전체 보고서 목록이나 메타데이터(태스크 상태, 날짜, 산출물 종류) 인덱스 파일이 없다.

### 영향

- 장기·다세션 운용 시 재개 비용이 선형 증가 → 실질적으로 장기 프로젝트를 포기하게 되는 인센티브 발생.
- Leader가 과거 결정을 오인하거나 중복 설계할 위험.
- 매 세션 재개마다 Fable/Opus급 토큰을 Comm.md 파싱에 낭비.

### 우선순위

**High** — 사용자 명시 최우선 관심사, 장기 팀원 운용의 물리적 전제조건.

### 구체 개선안

아래는 기존 제약(Leader 단독 작성, 워커는 final message 보고, append-only 원칙 유지)을 존중하는 설계다.

- **태스크 단위**: 태스크가 `done`으로 전환되는 순간 Leader가 Worker Report를 `comm-reports/T<id>.md`로 이동하고 Comm.md에서 제거. comm-index.md에 한 줄 요약 추가.

- **파일 크기 트리거**: Comm.md가 150줄을 초과하면 Leader가 다음 상태 변경 시 압축 작업을 우선 수행.

## 축③ 상시성·지속 세션 (세션 경계를 넘는 연속성)

### 현재 상태

- Step 0에서 Comm.md 재사용 원칙 명시(SKILL.md:40-41).
- 세션 시작 트리거: 사용자 `/clgem` 호출(SKILL.md description 트리거 참조).
- **"상시 가동/배경 상주" 개념 언급 없음**.

- **세션 중단 감지·복구 절차 없음**.

### 부족점

**P8. 세션 재개가 100% 사용자 수동 트리거 의존**

사용자가 `/clgem`을 호출해야만 재개된다. 팀원이라면 "내일 아침에 이 작업 계속해"라는 지시 이후 스스로 재개를 준비해야 하지만, 현재 구조에서는 사용자가 매번 명시적으로 재개를 요청해야 한다.

**P9. 재개 시 "어디서 멈췄나" 복원이 Leader의 판단에만 의존**

Status Summary가 재개 진입점이지만 (Comm.template.md:19-21), "이 시점에 in-progress 태스크가 있었다면 재개할 것인가, 처음부터 다시 계획할 것인가"의 판단 규칙이 없다. 워커가 실행 중이었다면 재배정이 필요한지 불분명하다.

**P10. 세션 수명 종료 조건 불명확**

Finishing 섹션(SKILL.md:148-154)은 목표 달성 시 종료를 정의하지만, "사용자가 중간에 대화를 끊고 나중에 재개"하는 시나리오에서 in-progress 태스크의 상태를 어떻게 보존하는지 명시가 없다.

### 영향

- 사용자가 대화를 닫으면 진행 중인 워커 태스크 상태가 불확실해짐.
- 재개마다 사용자가 "어디까지 했어?"를 설명해야 하는 어시스턴트 패턴으로 퇴행.

### 우선순위

**High** — 팀원 운용의 핵심 전제("상시 켜진 팀원")에 직접 충돌.

### 개선안

- **Session Checkpoint 규칙**: 매 상태 변경마다 Comm.md Status Summary를 "재개 명령어"를 포함한 형태로 갱신. 예: `현재: T3 in-progress(Scout/haiku), T4 todo. 재개 시: T3 결과 수집 후 리뷰 필요.`
- **인터럽트 핸들링**: in-progress 태스크가 있는 상태에서 세션이 종료되면 Comm.md에 `## Interrupted State` 섹션을 자동 기록 (Leader가 세션 종료 전 마지막으로 갱신).
- **재개 프로토콜 명시**: Step 0에 "in-progress 태스크 발견 시 워커를 재배정하되, 이전 워커 보고서가 있으면 우선 확인" 절차 추가.
- **장기적**: CronCreate 등 예약 실행과 연계하여 정해진 시간에 자동 재개하는 훅을 clgem 위에 얹는 구조 검토(스킬 수정 아닌 harness 레벨).

Leader는 사용자의 지시 없이 무엇을 할 수 있는가? 예를 들어 "Open Items에 적힌 미해결 항목을 다음 루프에서 자동으로 태스크화"하는 것이 허용되는가? 현재 규칙에 없다.

**P12. 약속된 일(committed follow-up)의 추적 장치 없음**

Leader Decision Log에 "다음 루프에서 X를 검토한다"는 결정을 기록할 수 있지만, 이것이 실제로 다음 루프에 태스크로 이어지는 것을 강제하는 메커니즘이 없다. Open Items 섹션이 있지만 "언제 처리하는가"의 정책이 없다.

**P13. 안전·승인 경계 정의 없음**

팀원이 자율 행동을 하려면 "이것은 승인 없이 해도 되는가"의 경계가 명확해야 한다. 현재 스킬에 이 경계가 없으므로, 능동성을 추가하면 의도치 않은 범위 침범이 발생할 수 있다.

### 영향

- clgem이 항상 사용자 지시 대기 모드에 머묾 → 어시스턴트 패턴과 구조적으로 동일.
- Open Items가 쌓여도 자동으로 태스크화되지 않아 실질적 방치 위험.

### 우선순위

**Med** — 상시성(축③)이 해결된 후 순차적으로 필요한 층위.

### 개선안

- **Committed Action 필드**: Leader Decision Log에 `next_action: <태스크 또는 "없음">` 필드 추가. 세션 재개 시 이 필드가 있는 미완료 항목을 자동으로 Task Board에 추가.
- **자율 행동 허용 범위(Autonomy Tier)** 정의를 SKILL.md에 추가:
  - **Tier 0 (항상 허용)**: 리뷰 실행, Comm.md 갱신, 상태 기록.
  - **Tier 1 (이전 루프에서 ACCEPT된 결정의 연장)**: 동일 패턴의 태스크 재배정.
  - **Tier 2 (사용자 확인 필요)**: 아키텍처 변경, 새로운 태스크 유형 추가, 외부 시스템 접근.
- **Open Items 처리 정책**: 루프 시작 시 Open Items를 점검하고, 해결 가능한 항목이 있으면 "이번 루프에 포함할까요?"를 사용자에게 묻는 단계를 Step 3 앞에 삽입.

## 축⑤ 협업 인터페이스 (사람·타 에이전트·외부 시스템과의 표준 입출력)

### 현재 상태

- 사람 ↔ Leader: `/clgem` 호출 + 대화.
- Leader ↔ 워커: Agent tool + worker prompt template (SKILL.md:116-134).
- 워커 → Leader: final message STATUS/CHANGED/EVIDENCE/CONCERNS 블록 (SKILL.md:129-132).
- Leader ↔ 외부 리뷰어(agy): Bash CLI `agy -p "<prompt>"` (antigravity-review.md:14-16).
- Leader → 사용자: 자유형 대화 요약.

### 부족점

**P14. 사용자 ← Leader 출력 포맷이 비표준**

Leader가 사용자에게 보고하는 방식이 "자유형 대화"다. 팀원이 팀에 정기 보고할 때의 표준 형식(예: 주간 업무 보고)이 없다. 사용자가 현재 상태를 구조적으로 파악하기 어렵다.

**P15. 외부 시스템 연계 인터페이스 없음**

Slack, 이메일, 캘린더, 외부 API 등과의 연결 정의가 없다. 팀원이라면 협업 툴에서 알림을 보내거나 받을 수 있어야 한다. MCP 도구들이 환경에 존재하지만(Slack MCP 등), clgem이 이를 활용하는 규칙이 없다.

**P16. 타 에이전트 시스템(다른 clgem 세션 등)과의 인터페이스 없음**

단일 Leader + 워커 팀 모델이므로, 여러 프로젝트가 병렬로 진행될 때 인터-팀 통신 메커니즘이 없다.

### 영향

- 사용자가 상태를 파악하려면 항상 Leader에게 직접 물어봐야 함 → 비동기 협업 불가.
- 외부 이벤트(슬랙 메시지, 캘린더 이벤트)가 clgem 루프에 입력으로 들어올 방법 없음.

### 우선순위

**Med** — 기본 팀원 운용에는 부차적이지만 실제 팀 통합에는 필수.

### 개선안

- **Leader 정기 보고 형식** 정의: 루프 완료 시 구조화된 요약을 사용자에게 제공.
  ```
  ## 루프 N 완료 보고
  - 완료 태스크: T1(PASS), T2(CONDITIONAL→수정 완료)
  - 진행률: 60%
  - 다음 루프 예정: T3(Scout), T4(Implementer)
  - 확인 필요 사항: OQ1 — [설명]
  ```
- **MCP 연계 옵션**: Comm.md의 Open Items에 `notify: slack#channel` 같은 메타데이터를 Leader가 기록하면, 사용자나 harness가 실행하는 규칙으로 처리. (스킬이 직접 MCP를 호출하도록 하면 권한 범위가 불명확해지므로, "메타데이터 기록 + 외부 harness 처리" 구조 권장.)

## 축⑥ 신뢰·책임·권한 (위임 가능한 권한 범위, 감사/롤백)

### 현재 상태

- agy 리뷰 게이트가 신뢰 메커니즘의 핵심 (antigravity-review.md:1-8).
- append-only + never delete 원칙이 감사 추적(audit trail) 역할 (SKILL.md:145-146).
- Leader Decision Log가 결정 근거 기록 (SKILL.md:103-105).
- **워커의 권한 범위(파일 접근, 외부 시스템 접근 등) 정의 없음**.
- **롤백 절차 없음**.
- **두 번의 REDO 이후 에스컬레이션만 있고, 자동 중단 없음** (SKILL.md:110-114).

### 부족점

**P17. 워커 권한 범위 미정의**

워커가 어느 디렉터리를 읽고 쓸 수 있는지, 어떤 명령어를 실행할 수 있는지가 Leader의 프롬프트에만 의존한다. "DO NOT" 섹션이 있지만 이것이 강제(enforcement)가 아니라 지침(guidance)이다.

**P18. 롤백 절차 없음**

Implementer 워커가 코드를 수정한 뒤 REDO 결정이 나와도, 이전 상태로 복구하는 절차(git revert 지시, 체크포인트 등)가 스킬에 명시되지 않았다.

**P19. 감사 로그가 Comm.md에 혼재**

append-only 원칙 덕분에 결정 이력이 남지만, 보안·컴플라이언스 감사를 위한 별도 감사 로그 포맷(who decided what when with what evidence)이 체계적이지 않다.

### 영향

- 실수한 워커의 결과가 파일시스템에 남아있고, Leader가 수동으로 정리를 지시해야 함.
- 장기 운용 시 "언제 누가 무엇을 결정했는가"를 Comm.md에서 찾는 비용 증가.

### 우선순위

**Low** — 단기 프로젝트에서는 agy 리뷰 게이트로 충분; 장기·팀 운용에서 필요.

### 개선안

- **REDO 시 롤백 지시 추가**: SKILL.md Step 3-4에서 REDO 결정 시 Leader가 다음 워커 프롬프트에 "이전 변경을 git으로 되돌리고 시작하라" 지시를 포함하도록 명시.
- **워커 기본 권한 정책**: agents.md에 각 역할의 기본 접근 범위 추가. 예: Scout = read-only; Mechanic = workspace write만; Implementer = workspace read/write + shell 실행.
- **Decision Log 구조화**: 각 항목에 `[날짜][역할][결정유형: ACCEPT/REDO/SUPPLEMENT][태스크id][한줄근거]` 포맷 적용.

## Top 3 우선 개선 과제

### 1위 — 선택적 로딩 가능한 계층형 저장소 구조 도입 (축①)

**근거**: 사용자 명시 최우선 관심사. 현재 Comm.md는 append-only이고 토큰 관리 메커니즘이 전혀 없다(SKILL.md:145-146, Comm.template.md 전체). 50+ 태스크 장기 프로젝트에서 재개 비용이 선형으로 증가해 장기 팀원 운용이 물리적으로 불가능해진다. 축① 개선안의 comm-index.md + comm-summary.md + Comm.md 3계층 구조와 선택적 로딩 규칙이 가장 즉각적 효과를 낸다.

**실행 난이도**: 낮음 — Comm.template.md 업데이트 + SKILL.md Step 0에 프로토콜 추가. 워커 행동 변경 불필요.

### 2위 — Session Checkpoint + 재개 프로토콜 명시 (축③)

**근거**: "상시 켜진 팀원"의 핵심은 사용자 없이도 상태가 보존되는 것이다. 현재 세션 종료/재개 규칙이 "Comm.md가 있으면 읽어라"에 그친다(SKILL.md:40-41). Interrupted State 섹션, in-progress 태스크 복원 절차, 재개 명령어 포함 Status Summary가 없으면 매 세션이 사실상 새로 시작이다.

**실행 난이도**: 낮음 — SKILL.md Step 0 확장 + Comm.template.md에 Interrupted State 섹션 추가.

### 3위 — Committed Action + Autonomy Tier 정의 (축④)

**근거**: 팀원이 "다음에 할 일"을 스스로 기억하고 실행 준비하는 것이 어시스턴트와의 핵심 차이다. 현재 Decision Log가 미래 행동을 기록할 수 있지만 이를 강제 실행으로 연결하는 메커니즘이 없다(SKILL.md:100-105). Autonomy Tier는 능동성의 안전 경계를 정의해 무분별한 자율 행동 없이 팀원성을 구현한다.

**실행 난이도**: 중간 — SKILL.md에 Tier 정의 및 Step 3 앞에 Open Items 점검 단계 추가 필요. 워커 행동에는 영향 없음.

## 분석의 한계 및 리뷰어 검증 포인트

1. **실운용 데이터 부재**: 실제 장기 프로젝트에서 Comm.md가 몇 줄까지 커지는지, 실제 재개 토큰 비용이 얼마나 되는지를 측정한 데이터가 없다. 150줄 압축 트리거 등의 수치는 추정이다.
2. **comm-index.md / comm-summary.md 추가 파일이 Leader 작성 부담을 늘림**: 현재 Comm.md 단독으로도 매 상태변경마다 갱신 부담이 있다(SKILL.md:144). 파일 수 증가가 Leader 토큰 비용을 오히려 높일 가능성을 검증해야 한다.
3. **세션 경계는 Claude Code harness 레벨 문제**: 상시성(축③) 개선의 일부(자동 재개 트리거)는 스킬 수준이 아니라 Claude Code hooks/CronCreate 수준에서 구현해야 한다. 스킬만으로 완전 해결 불가.
4. **Autonomy Tier의 실제 강제 수단 없음**: LLM에게 "Tier 2는 묻고 해라"고 지시해도 enforcement 메커니즘이 아니라 지침이다. 이를 인식하고 설계해야 한다.
5. **agy 리뷰 게이트 의존성**: 신뢰·책임(축⑥) 개선의 상당 부분이 agy가 정상 작동한다는 가정 위에 있다. agy 없는 환경에서의 fallback 시나리오를 더 강화해야 할 수 있다.
