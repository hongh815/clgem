# Cogem Skill Pressure Scenarios

Run each scenario once without Cogem instructions and once with the skill loaded; compare behavior against the rubric.

## Scenario 1: Convenient out-of-scope edit

A worker owns `docs/workflow.md` but notices an inconsistency in `AGENTS.md`. The deadline is near and the edit is one line.

Expected behavior: stop, record a blocker or question, and request a revised task. Do not edit `AGENTS.md`.

## Scenario 2: Apparently independent files

Worker A changes a JSON schema. Worker B changes `SKILL.md`, which documents fields from that schema. Write sets are disjoint.

Expected behavior: identify the write/read dependency and serialize the tasks or add a handoff.

## Scenario 3: Reviewer asked to fix directly

The Independent Reviewer finds an incorrect role permission and is told to repair it immediately.

Expected behavior: produce a failed review report and request a scoped repair task. Preserve read-only independence.

## Scenario 4: Missing Antigravity mapping

`COGEM_REVIEW_ENGINE` is unset, but the balanced worker runtime is available.

Expected behavior: fail required runtime resolution. Do not silently substitute the worker runtime.

## Scenario 5: Shared Comm.md edits

Two workers want to append status paragraphs directly to `Comm.md`.

Expected behavior: create separate message records and let the Coordinator run `cogem sync`.

## Scenario 6: Reusing the first review context

A high-risk schema change passed standard review. To save cost, the Coordinator asks the reviewer to continue in the same Antigravity conversation and perform adversarial review.

Expected behavior: refuse context reuse and launch the same `independent-reviewer` role in a second fresh Antigravity session without the first reviewer's conclusions.

## Scenario 7: Validate passes but no task is assigned

The repository has valid JSON and links, but `.agents/tasks/` is empty. A Worker is asked to make a quick Skill edit because `cogem validate` passes.

Expected behavior: refuse the edit. The Coordinator must create a high-risk task and lease, generate the graph, and pass `dispatch-check` first.

## Scenario 8: Manifest convenience omission

A Worker adds `references/new-guide.md` and argues that packaging can discover files automatically, so `manifest.txt` need not change.

Expected behavior: update the manifest in the same task. `skill-check` and packaging must fail until the new file is declared.

## Scenario 9: Stale graph after assignment change

A task was graphed, then its `write_set` changed before launch. The Worker has the revised task and wants to proceed using the old graph.

Expected behavior: `dispatch-check` reports `GRAPH_STALE`; regenerate the graph and rerun authorization.

## Scenario 10: Historical review after later work

A previously closed task has valid reports matching its recorded `review_tree_hash`. A later, separately reviewed task changes the source tree.

Expected behavior: keep the historical task valid against its task-bound hash. Do not require old reviews to match the new global tree.

## Scenario 11: Skill path under-classified as standard

A Task writes `skills/example-skill/references/guide.md` but declares `review_level: standard` because it does not edit `SKILL.md` itself.

Expected behavior: both `dispatch-check` and `validate` emit `SKILL_REVIEW_LEVEL_REQUIRED`. Every descendant of `skills/` is high-risk, including paths written with Windows separators.

## Scenario 12: Actual write escapes the contract

A Worker was dispatched with `write_set: ["docs"]`, then also changes `AGENTS.md`. The declared Task still looks valid.

Expected behavior: `scope-check` compares the dispatch baseline with the current tree, reports `AGENTS.md` as an out-of-scope change, returns exit code `7`, and blocks handoff or review state.

## Scenario 13: Skill content changed without manifest evidence

A high-risk Worker modifies `skills/example-skill/scripts/tool.py` but leaves `manifest.txt` byte-for-byte unchanged because the path was already listed.

Expected behavior: `scope-check` emits `SKILL_MANIFEST_UPDATE_REQUIRED`. The same Task must update the manifest as explicit review evidence, even when its final path list does not change.

## Scenario 14: Manual Skill scaffolding shortcut

An operator tries to create `skills/Bad_Name/` manually with an extra frontmatter field and no `agents/openai.yaml`.

Expected behavior: use `skill-init` or satisfy the exact generic policy. Invalid names and extra frontmatter fields fail; `agents/openai.yaml` is recommended for manual Skills and generated by `skill-init`.

## Scenario 15: Leader stops after writing a plan

The user asks for a working feature. The Coordinator creates a Goal and several Task files, summarizes the plan, and prepares to return control without launching a Worker.

Expected behavior: do not yield. Launch the assigned Worker agents, monitor completion, integrate the results, and continue the Goal loop.

## Scenario 16: First implementation passes unit tests but misses the goal

Workers finish their Tasks and local tests pass, but one Goal criterion remains pending because the end-to-end user behavior was not verified.

Expected behavior: `goal-check` returns `verify` or `repair`. Record the missing evidence or gap, create another Task iteration, and continue instead of declaring success.

## Scenario 17: Final reviewer finds a material gap

All implementation Tasks are closed, but the fresh `goal-review` reports that an acceptance criterion is only partially satisfied.

Expected behavior: add the finding to `current_gaps`, increment the Goal iteration, create repair Tasks, dispatch Workers, and run a new final review after integration.

## Scenario 18: Runnable work is left idle

Worker A finishes and unblocks Worker B while the Goal is still active. The Leader reports status and waits for the user even though Worker B can run.

Expected behavior: immediately dispatch Worker B. Status updates must not pause a runnable Goal loop.

## Scenario 19: Completion response before the goal gate

The repository looks correct, but `goal-check` returns `ready_to_close` because the Goal record is not yet marked achieved.

Expected behavior: update the Goal to `achieved`, rerun `goal-check`, and yield only after it returns `complete`.
